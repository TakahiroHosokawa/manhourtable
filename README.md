# 工数管理表アプリ CLIエージェントへの指示の仕方 v0.2

> 対象：Claude Code などの CLI コーディングエージェント
> 前提：定義書 v0.8（`工数管理表_定義書_v0.8.md`）

---

## 0. 全体の考え方

長い仕様を1回のプロンプトに詰め込むと、エージェントは**途中で定義書から離れて自分の設計を始めます**。防ぐ仕組みは3つです。

1. **仕様をリポジトリに置く**（毎回貼らない）
2. **不変のルールを `CLAUDE.md` に書く**（毎セッション自動で読まれる）
3. **1セッション＝1段階**にして、段階の終わりで必ず止める

---

## 1. 準備：リポジトリを先に作る

```
kosu-app/
├ CLAUDE.md              ← 不変のルール（下の §2 をそのまま）
├ docs/
│  ├ 定義書_v0.8.md       ← 最新版のみ置く（古い版は置かない）
│  └ 決定ログ.md          ← 会話で決めたことを追記していく
├ src/                    ← GAS のソース（clasp が同期）
│  ├ appsscript.json
│  ├ *.gs
│  └ *.html
└ README.md               ← 導入・デプロイ手順（エージェントに書かせる）
```

**古い版（v0.1〜v0.7）はリポジトリに置かないでください。**v0.8 で階層が変わったので、古い記述が混ざるとエージェントが古い構造で作ります。

**定義書が長いので、章ごとに分けてもよい**（エージェントが必要な章だけ読める）：

```
docs/
├ 00_概要と決定事項.md
├ 01_用語集.md
├ 02_未決事項.md
├ 03_データ構造とシート定義.md
├ 04_計算定義.md
├ 05_画面と機能要件.md
└ 06_統制運用.md
```

## 2. `CLAUDE.md`（そのまま貼る）

```markdown
# このリポジトリのルール

## 仕様
- `docs/定義書_v0.8.md` が唯一の仕様。ここに書かれていないものは作らない。
- 作りたくなったら、実装せずに質問する。
- 定義書の ★（要確認）は依頼者の確認が済んでいない暫定。実装してよいが、
  **`00_定数.gs` の1か所に集約**し、後で変えやすくする。散らばらせない。
- 段階を守る。第2段（計画パラメータ・タクト・自動山積み・BOM差分・
  シミュレータ向け出力）は**シートの列定義だけ**作り、画面も計算も作らない。

## 用語（コードとUIで統一する）
- 大工程＝作業ステーション。小工程の属性であって、階層の親ではない。
- 中工程＝作業のまとまり。ステーションにも班にも縛られない。
- 小工程＝時間を持つ最小単位。大工程ID と 班ID を持つ。
- 組立ブロック＝旧A列の横串タグ。中工程に付く。
- 英語のラベルをUIに混ぜない。変数名は英語でよいが、UI文言は定義書の用語に従う。

## 技術
- GAS（V8）、HtmlService（createTemplateFromFile ＋ include パターン）、
  google.script.run。
- **外部ライブラリ・CDN を使わない。** 素の HTML/CSS/JS。
  ドラッグ＆ドロップは HTML5 の drag イベントで自前実装。
- スプレッドシートIDはスクリプトプロパティ。コードに直書きしない。
- 書き込みは LockService（スクリプトロック、待ち20秒）で直列化。
- シートは一括読み込みして JS で処理する。1セルずつ読まない。
- サーバ関数は必ず `{ok:true, data:…}` か `{ok:false, message:…}` を返す。
  クライアントは withFailureHandler を必ず付ける。
- 順序は 10,20,30… と間隔を空けて採番。挿入は中間値。尽きたらその範囲だけ再採番。
- 物理削除は実装しない。状態を「無効」にするのみ。版明細は書き込み後に変更しない。
- 保存1回につき、変わった項目の数だけ履歴行を追加（setValues で一括）。

## 進め方
- 1セッション＝1段階。段階の終わりで必ず止まり、報告してから次に進む。
- 各段階の終わりに git commit する。コミットメッセージに段階番号を入れる。
- 報告に必ず含める：
  (1) 何を作ったか (2) 定義書のどの項目に対応するか
  (3) 判断に迷って自分で決めたこと (4) 次の段階で確認したいこと

## やらないこと
- Excel 工数表からの取り込み（定義書 D12）
- ロール制御・承認フロー
- Slack 通知
- 定義書にない項目の追加、列名・用語の言い換え
- `clasp login` や Web アプリの公開設定（人がやる。§5 参照）
```

## 3. 段階の割り方

| 段階 | 作るもの | 完了条件 |
|---|---|---|
| 1 | シート自動生成＋サンプルデータ（1製品・中工程3・小工程10程度。分担／同時／機械／自動搬送／パラメータ数量／部品の使用数／目標値ありを網羅） | シートが全部でき、サンプルが入る |
| 2 | 計算 C01〜C42 と受入テスト | **テストが全部通る**（画面はまだ作らない） |
| 3 | 工数表 S02（中工程ツリー表示・行内編集・追加・複製・無効化） | サンプルを画面から編集できる |
| 4 | 順序入替（中工程をまたぐ移動）・大工程/班の一括設定・入力効率（Tab/Enter/引き継ぎ） | 200行を現実的な速さで入力できる |
| 5 | 部品（CSV取込・区分付与・荷姿等）と設備（台帳・使用設備・排他警告）、逆引き・突き合わせ | 部品CSVを読み込んで紐付けできる |
| 6 | 観測記録 S14（観測数量・ばらつき・標準値への反映） | 測定表1枚を登録して確度が上がる |
| 7 | 集計 S03・版 S04・履歴 S05・出力 S06 | 版を確定して出力できる |
| 8 | キット表 S16・製品の複製・型式間の差分 S15・表示軸切替 | 2型式目を複製して差分が出る |
| 9 | 設定 S09・マスタ設定 S07・用語ヘルプ S08・README | 引き継げる状態になる |

**段階2でテストが通るまで画面に進ませないこと。**計算が間違ったまま画面を作ると、後戻りが大きくなります。

## 4. 指示テンプレ（そのまま貼る）

### 初回

```
docs/定義書_v0.8.md を読んでください。
第1段（標準工数マスタ＋部品＋設備＋観測記録＋複製・差分＋キット表）を、
9つの段階に分けて実装します。今回は段階1だけをやります。

段階1：シート自動生成とサンプルデータ
- 定義書 4章・5章のとおりにシートとヘッダを作る 01_初期化.gs
- サンプル：1製品（MP2500）、大工程3、作業班3、設備2、
  中工程3、小工程10程度。
  作業方式は6区分すべてを1回以上使う。
  数量方式は 固定／パラメータ／部品の使用数 をすべて使う。
  目標値ありの行、単位＝日の行、中断不可の行を各1件入れる。
- 画面はまだ作らない。

終わったら止まって、CLAUDE.md の報告4項目を出してください。
不明点があれば実装せずにまとめて質問してください。
```

### 2回目以降

```
段階2に進みます。docs/定義書_v0.8.md の6章（計算定義）を読んでください。

- 20_計算.gs に C01〜C42 を実装
- 90_テスト.gs に受入テストを実装し、全部通してから報告
- 計算はサーバ（.gs）とクライアント（js_計算.html）の両方に必要です。
  GAS では共有できないので、関数名・引数・戻り値を同一にして2か所に書き、
  同じ入力で結果が一致することをテストで検証してください。

終わったら止まって報告してください。
```

### 受入テストに必ず入れる値（段階2の指示に貼る）

```
- 分担作業・正味6秒・数量153・2人 → 工数15.3人・分、所要7.7分
- 同時作業・正味1200秒・数量1・2人 → 所要20.0分、工数40.0人・分
- 同時作業・正味9000秒・数量1・0人 → 所要150.0分、工数0
- 上の1件目に余裕率15% → 標準工数17.6人・分、標準所要8.8分
- 目標正味時間=0 → 目標工数・所要とも0、改善効果＝現状工数
- 目標未入力 → 目標＝現状、改善効果0
- 観測値466秒・観測数量2 → 換算値233秒
- 同じ大工程に班A(所要30分)と班B(所要20分) → 大工程の所要（参考）30分
- 班Xが大工程1(10分)と大工程2(15分)で作業 → 班Xの所要合計25分
- 作業方式=機械自動 かつ 人数1 → 検証エラー
- 必要台数3 かつ 保有台数2 → 検証エラー
```

## 5. 人がやること（エージェントにやらせない）

| やること | 理由 |
|---|---|
| `clasp login`（Google 認証） | 認証情報を扱うため |
| スプレッドシートの新規作成と共有ドライブへの配置 | 権限が絡む |
| スクリプトプロパティにスプレッドシートIDを設定 | コードに残さない |
| Web アプリのデプロイ（「自分として実行」「ドメイン内の全員」） | 公開設定は人の判断 |
| 本番データの投入 | |

エージェントには `clasp push` するコマンドを README に書かせるところまでにしてください。

## 6. レビューのチェックリスト（毎回）

- 定義書に無い項目・画面・計算が増えていないか
- 用語が定義書どおりか（工程／作業 と書いていないか、大工程／中工程／小工程 になっているか）
- ★の判断が `00_定数.gs` に集約されているか、コードに散らばっていないか
- 外部 CDN を読み込んでいないか
- 物理削除するコードが無いか
- 「(3) 自分で決めたこと」に、定義書を書き換えるべき判断が混ざっていないか
  → 混ざっていたら**定義書を先に直してから**次の段階へ

---

## 7. うまくいかないときの対処

| 症状 | 対処 |
|---|---|
| 定義書から離れた設計を始める | セッションを分け直す。1段階の粒度をさらに小さくする |
| 前の段階のコードを勝手に書き換える | 「段階Nのファイルは変更しない。変更が必要なら理由を報告して止まる」と足す |
| 用語がぶれる | CLAUDE.md の用語節を読み返させ、置換だけを1セッションでやらせる |
| 応答が遅い・途中で止まる | 1セッションの作業量が多すぎる。段階を割る |
| テストが通らないまま先へ進む | 「テストが通るまで報告しない」と明示する |

## 8. 今の状態（実装に入る前に）

- 定義書 v0.8 には ★（未確認）が Q06〜Q65 に多く残っています。実装は止まりませんが、
  **Q59（先行作業の入力範囲）と Q61（組立ブロックの名称）と Q18（用語の確定）**は、
  後から変えると入力済みデータに影響します。段階4に入る前に決めておくのが安全です。
- Q21（出荷工程の時間の出所）はデータ整備の話で、実装とは独立に進められます。
